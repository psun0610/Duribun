# 테스트 규칙 — 이 저장소의 테스트는 일반적이지 않습니다

Vitest(`environment: 'node'`, `include: ['src/**/*.test.ts']`)로 돌지만 **실행되는 코드를 테스트하지 않습니다.**
테스트는 마이그레이션 SQL과 소스 파일을 `readFileSync`로 읽어 **문자열이 들어 있는지 assert**합니다. DB도, 렌더링도, 목킹도 없습니다.

```ts
expect(initialSchemaSql).toContain('public.is_couple_place_public_ready')
expect(shareTypesSource).not.toContain('oneLineReview')
```

## 여기서 따라오는 결과

- **정책 이름, 함수 이름, 상수 문구, 타입 필드명을 바꾸면 런타임이 아니라 테스트가 깨집니다.** 이름 변경 시 대응하는 `.test.ts`도 함께 고치세요.
- **파일을 옮기거나 이름을 바꾸면 테스트가 `ENOENT`로 죽거나 조용히 빈 문자열을 검사합니다.** 실제로 라우트를 `/app/places`·`/app/friends`·`/app/explore`로 분리했을 때 테스트 2개가 `src/app/app/page.tsx`를 계속 읽어 깨진 적이 있습니다. 리팩터링 후에는 반드시 **전체** `pnpm test`를 돌리세요. 파일을 지정해 일부만 돌리면 이런 파손을 놓칩니다.
- **테스트 통과 ≠ 동작 확인.** 로직 버그, 잘못된 쿼리, 깨진 UI는 이 테스트가 절대 잡지 못합니다. 실제 검증은 Supabase에 연결해 화면에서 확인해야 하고, 그렇게 못 했다면 그 사실을 사용자에게 말해야 합니다.
- **테스트가 스펙이 아니라 현재 코드를 따라가지 않도록 주의하세요.** 리뷰 상태 문구가 스펙에서 벗어났을 때, 테스트가 벗어난 문구를 그대로 `toContain`으로 고정해 버려 아무도 눈치채지 못했습니다. 문구를 검사할 때는 `docs/product-decisions.md`를 기준으로 삼으세요.

## 새 테스트를 쓸 때

- 기존 방식을 유지합니다: 마이그레이션 SQL과 관련 소스를 읽어 규칙이 실제로 코드에 박혀 있는지 확인.
- 부재 확인(`not.toContain`)이 특히 유용합니다 — 비공개 필드가 공개 타입에 새지 않았는지 등.
- 기능이 "존재한다"가 아니라 "연결돼 있다"를 확인하세요. 함수가 정의만 되고 호출되는 곳이 없어도 존재 검사만으로는 통과합니다 (`delete_expired_disconnected_couples`가 실제로 그런 상태였습니다).
- 순수 함수(`utils/`)에는 일반적인 단위 테스트를 씁니다. 이쪽이 진짜 로직 테스트입니다.
